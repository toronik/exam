=== stable under [[e-stable-under]]

An example marked `[\{stable-under}]` runs once per perturbation named in the marker, and every case
has to end the way the example does. `duplicate` performs every delivery of the case twice, `reorder`
performs them in the opposite order.

<<e-outline,An outline>> says that these cases differ; this says that the outcome does not depend on
how the deliveries arrived.

.Usage
[source,asciidoc]
--
include::core-invariance.adoc[tags=stable]
--

=====
//tag::stable[]
.Remembering a name
[{stable-under} duplicate reorder]
====
Given:: [{exec}remember(#TEXT)]`Bob` and [{exec}remember(#TEXT)]`Ann` are remembered
Then:: `Bob` is remembered [{eq}timesRemembered('Bob')]`1` time,
and [{eq}namesRemembered()]`2` names in all
//end::stable[]
====
=====

What is perturbed is *the deliveries of the document*, not the behaviour of the system. So `reorder`
over one `[\{mq-set}]` table of three messages reorders nothing - that is one delivery; time cannot
be perturbed at all; and over `[\{exec}]` the property checked is that calling the fixture twice is
safe, which is weaker than a broker delivering twice. A delivery is anything executed that is not
excepted - `e-mq-set`, `e-execute` and `e-http` by default - and the line is not clean by command
name: `e-http` both sends and checks, `e-execute` also sets things up.

A repetition that is honest is excepted: everything inside a `[\{stable-except}]` block is left as it
stands.

=====
//tag::except[]
.Delivered once on purpose
[{stable-under} duplicate]
====
[{exec}remember(#TEXT)]`Ann` is remembered.

[{stable-except}]
--
[{exec}deliver(#TEXT)]`Bob` is delivered, once and only once.
--

`Ann` is remembered [{eq}timesRemembered('Ann')]`1` time
and `Bob` delivered [{eq}timesDelivered('Bob')]`1` time.
//end::except[]
====
=====

A green case proves little on its own: the same body passing again is what one expects of a body that
ignores its input. The guard is a body that is *not* invariant - delivering a name appends it - kept
in the suite by `{ExpectedToFail}`. Were duplication to stop happening, this example would pass, and
an example expected to fail that did not is a broken build.

=====
//tag::not-stable[]
.Delivering a name twice delivers it twice
[{stable-under} duplicate ExpectedToFail]
====
Given:: [{exec}deliver(#TEXT)]`Bob` is delivered
Then:: `Bob` is delivered [{eq}timesDelivered('Bob')]`1` time
//end::not-stable[]
====
=====

.Refused, and how to add a perturbation of your own
[{collapse}]
=====
A marker naming no perturbation Exam knows is refused with the known ones listed, and so is a
perturbation with nothing to perturb: a case that verifies nothing the example already verifies must
not be published as a verified property.

What only the fixture can do - restart the application, take a dependency away - is a `Perturbation`
of the project's own, registered with `withPerturbations(...)`:

[source,kotlin]
----
object Restart : Perturbation {
    override val name = "restart"
    override val effect = "the application was restarted between the deliveries of this case"
    override fun applies(deliveries: Int) = deliveries > 1
    override fun perturb(deliveries: List<Element>) = deliveries.drop(1).forEach { delivery ->
        (delivery.parent as Element).let { parent ->
            parent.insertChild(
                Element("div").apply { addExamAttr("execute", "restartSut()") },
                parent.indexOf(delivery)
            )
        }
    }
}
----

`restartSut()` is a method of the fixture, so nothing about restarting a system leaks into the
framework.
